# IELTS Coach Test Coverage Matrix

This document inventories the current automated test strategy. A listed test layer means the workflow or test family is intended to exercise that area; it does **not** mean every edge case is covered or currently passing. Check the referenced test files and latest GitHub Actions run before making a status claim.

## Test environments

| Layer | Workflow / location | Environment | Allowed use |
|---|---|---|---|
| Backend API and service tests | `.github/workflows/ci.yml`, `backend/tests/` | Ephemeral PostgreSQL 16 service in GitHub Actions; migrations applied first | Authentication, API/service behavior, validation, persistence, regression tests |
| Frontend production build | `.github/workflows/ci.yml` | Node 20 build job | TypeScript/Next.js compilation and build-time checks |
| Full browser E2E | `.github/workflows/browser-smoke.yml`, `frontend/tests/e2e/` | Ephemeral PostgreSQL 16 database named `ielts_coach_e2e`, migrated and seeded; API and frontend built for CI | State-mutating end-to-end flows with disposable data |
| Deployed public-page smoke | `.github/workflows/production-browser-smoke.yml`, `frontend/tests/e2e/production-smoke.spec.ts` | Explicit deployed URL; no isolated database is attached | Read-only GET/navigation, rendering, serious/critical WCAG A/AA axe scans on login and registration, 390px overflow checks, and unauthenticated redirects from protected skill routes |

## Current known Playwright suite and workflow behavior

- Playwright test directory: `frontend/tests/e2e/` includes the existing skill, mobile, keyboard, accessibility, and failure-path specs plus `cross-browser-stateful.spec.ts` for authenticated state retention and a persisted Reading submission/review journey. Verify current test counts and pass/fail in Actions.
- Configuration: `frontend/playwright.config.ts`.
- CI full stateful browser suite: Chromium runs the complete suite with retry enabled; Firefox and WebKit run the focused `cross-browser-stateful.spec.ts` journeys against their own isolated PostgreSQL service and seeded content. The deployed read-only public-page smoke suite remains independent and runs in Chromium, Firefox, and WebKit. Traces, screenshots, and video are retained on failures according to config.
- The isolated browser workflow applies Alembic migrations, runs `backend/scripts/seed_e2e_practice.py`, starts FastAPI against its test PostgreSQL service, builds the frontend with `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000/api/v1`, and runs `npm run test:e2e`. This suite may mutate data and must stay pointed at disposable CI data.
- The browser smoke workflow runs `npx playwright test tests/e2e/production-smoke.spec.ts` in Chromium, Firefox, and WebKit against a local frontend build. It checks public login/registration forms, 390px horizontal overflow, and that protected skill routes load without mutating requests. It does not submit forms, sign in, create accounts, start practice attempts, or save drafts; auth redirect behavior is covered in the stateful E2E suite.
- Do not set `PLAYWRIGHT_BASE_URL` to a production URL when running the full state-mutating E2E suite. The production workflow's dedicated spec is the only suite intended for deployed read-only checks.
- Failure diagnostics are uploaded as workflow artifacts when the corresponding job fails.

## Manual screen-reader review

`docs/testing/manual-screen-reader-review.md` defines a repeatable manual review protocol for authentication, dashboard navigation, Reading, Listening, Writing, Speaking, review screens, status/error announcements, focus behavior, and assistive-technology/browser metadata. The checklist is a planned manual procedure; completion requires a tester to record actual AT/browser versions and findings. It does not claim that screen-reader testing has already been performed or establish WCAG conformance.


## Updating this matrix

When changing test coverage:

1. Link the exact test file(s) and describe the assertion that proves the behavior.
2. Distinguish API/service tests from end-to-end browser tests.
3. Note whether the test uses isolated fixtures, mocked external services, or live dependencies.
4. Record gaps honestly; do not infer coverage from a route existing or from a successful build.
5. Use actual GitHub Actions results for pass/fail status. Do not store transient status such as “currently green” as a permanent coverage fact.


## Keyboard task-flow extension

`frontend/tests/e2e/keyboard-practice-flows.spec.ts` verifies keyboard-only Reading answer entry and submission, Listening answer selection and section navigation, Writing task-tab switching and submission, and Speaking preparation, transcript entry, save/advance, and completion. Stateful interactions use isolated CI PostgreSQL; Writing and Speaking evaluations are mocked. This complements `keyboard-accessibility.spec.ts`, which covers dashboard navigation and operating an active control.


## API ownership audit

`backend/tests/test_api_ownership_audit.py` verifies cross-user isolation for Reading, Listening, Writing, and Speaking: foreign users cannot list another user's attempts, retrieve attempt details, submit Reading/Listening attempts, edit Writing drafts, overwrite Speaking transcripts, or evaluate another user's Speaking response. The tests use registered test accounts and seeded records in the isolated backend test database. API ownership gaps outside these exercised operations remain subject to route-by-route review.


## Stateful cross-browser journeys

`frontend/tests/e2e/cross-browser-stateful.spec.ts` runs in Firefox and WebKit against the isolated CI PostgreSQL database. It verifies registration/authentication, session and token retention across skill navigation and reload, and a seeded Reading attempt submitted, its persisted detail verified through the authenticated API, then rechecked after browser reload (the review itself is a client-side view, not a deep-link route). The full state-mutating suite remains Chromium-only; deployed production smoke remains read-only.
